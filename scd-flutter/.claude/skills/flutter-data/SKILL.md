# Flutter data layer

Reference: **Flutter 3.44.0** · Dart SDK **3.12.x**. Package status is the most perishable
content in this plugin — every package claim carries its verification date, and the
persistence half is re-checked at each Flutter stable.

This skill answers **how to fill the Repository**, not whether it should exist.
`flutter-architecture` prescribes *that* a Repository exists and *which* boundaries it
respects; nothing there says how to talk to a server, map an error, or keep a token alive.

## Serialisation is generated by build_runner — macros are cancelled

Dart macros were **abandoned before shipping**. The official Dart blog post *"An update on Dart
macros & data serialization"* (Vijay Menon, 29 January 2025) states it verbatim
`[OFFICIAL, High]`:

> *"we've made the difficult decision to stop our work on macros… we are not seeing macros
> converging anytime soon toward a feature we are comfortable shipping"*

An agent working from pre-2025 material will reach for a macro-based `@JsonCodable` and produce
code that cannot compile. The path Dart put forward instead is **improved `build_runner`
generation and augmentations** — so serialisation goes through `json_serializable`, `freezed`
or `dart_mappable`, generated into `.g.dart` / `.freezed.dart` parts.

## Choosing a serialisation generator

`json_serializable` for plain DTOs, `freezed` on top of it for immutable models with unions and
`copyWith`, `dart_mappable` when polymorphism, generics and inheritance are the hard part. A
polymorphic payload needs a **discriminator key** in the JSON, or no generator can decide which
class to build. Treat an external API's nullability as untrusted: a non-nullable Dart field
throws inside the *generated* parser, where the stack trace blames generated code, not the
payload.

`dart run build_runner build --delete-conflicting-outputs` — the flag is not optional in
practice; omitting it is the recurring blocking error.

The generator comparison table (including the freezed 3.0 / generics friction, #1213), the
`watch` variant and the argument for hand-writing `fromJson` on a few small models are in
[`references/serialisation.md`](references/serialisation.md).

## Failures cross the boundary as Result, never as exceptions

`flutter-architecture` prescribes a sealed `Result` and forbids raw exceptions leaking out of
the Data layer. That contract only holds if **every** transport failure has a mapping — an
unmapped one escapes as an exception and violates the boundary the architecture already set.

| Transport failure | `dio` | `http` / `dart:io` | Maps to |
|---|---|---|---|
| Connect timeout | `DioExceptionType.connectionTimeout` | `TimeoutException` from your own `.timeout()` | Retryable network failure |
| Send / receive timeout | `sendTimeout`, `receiveTimeout` | idem | Retryable network failure |
| DNS, no route, offline | `connectionError` | `SocketException` | Offline / unreachable |
| 4xx | `badResponse`, status 400–499 | status code on the response | Client failure — **not** retryable |
| 401 / 403 | `badResponse` | idem | Auth failure, routed to the session logic |
| 5xx | `badResponse`, status 500–599 | idem | Server failure — retryable |
| Cancelled | `cancel` | your own cancellation signal | Cancelled, not an error to surface |
| Malformed body | parse throws | parse throws | Contract failure — a bug, not a network event |

Two consequences worth stating: **the status code alone is not the discriminator** — a
`connectionError` has no status at all — and **cancellation is not a failure**, so a UI that
renders every non-success variant as an error message will flash an error on every screen the
user leaves early.

`dio` 5 renamed `DioError` to `DioException` and `DioErrorType` to `DioExceptionType`; material
written before that rename does not compile.

## Timeouts, retry and cancellation

**There is no single timeout.** Connect and receive are separate limits answering different
questions — is the server reachable, and is it still sending? A 30-second receive timeout with
no connect timeout hangs for 30 seconds on an unreachable host.

**Retry is gated on idempotency, not on the error.** Replaying `GET`, `PUT` or `DELETE` is safe;
replaying `POST` duplicates whatever the server already did — an order, a payment, a message.
A retry policy that keys only on the status code and ignores the verb produces duplicated
server-side effects, and it does so invisibly, because the client saw a failure.

Retry the retryable classes above with **exponential backoff plus jitter**; a fixed delay
synchronises every client that failed at the same moment and re-creates the spike that caused
the failure.

**Cancellation is a lifecycle concern.** A request outliving the screen that started it wastes
work and can deliver a result into a disposed ViewModel. `dio` provides `CancelToken`; on `http`
the pattern is the caller's own signal. Either way the cancellation goes in `dispose`, alongside
`flutter-runtime`'s controller and subscription checklist.

## One refresh, not N

When several requests fail with 401 at the same instant, the naive interceptor fires one refresh
per request. Concurrent refreshes then invalidate each other's tokens and log the user out — the
most common and most expensive bug in this layer.

The shape that works: **the first 401 starts the refresh; every later 401 waits on that same
in-flight refresh and replays once it completes.** A single `Completer` held by the interceptor
does it. Add a replay guard — a flag on the request — so a request that already retried once
cannot loop.

> **[PRACTITIONER, Medium] — not a prescription.**
> Flutter prescribes nothing here. `dio` supplies `QueuedInterceptorsWrapper`, which serialises
> error handling so simultaneous 401s stack behind one refresh, and the "flag + queue /
> `Completer`" pattern is practitioner-established. The API exists; the pattern is not endorsed
> as the recommended approach.
> *What would lift this:* an official Flutter prescription, or `dio` documentation raising
> `QueuedInterceptorsWrapper` from an API to a recommended pattern.

## Target http.Client, not dart:io HttpClient

**Platform HTTP clients implement `http.Client` only** — never `dart:io`'s `HttpClient`
`[OFFICIAL, High]`. `CronetClient` (Android) and `CupertinoClient` (iOS/macOS) delegate to the
OS networking stack, which buys HTTP/3, system proxy and VPN handling, and a configurable
native cache. Code typed against `HttpClient`, as older examples are, cannot accept them.

So type every seam against `http.Client` and inject the implementation. On `dio`, the bridge is
`native_dio_adapter`, which delegates to the same two packages `[MAINTAINER]`.

Swapping in a platform client **changes behaviour**, not just performance: requests start
honouring a system VPN or proxy, and caching follows platform rules. That is usually the point,
and it is worth knowing before a support ticket says "it works on wifi but not on the corporate
network".

## Offline-first

Flutter publishes a dedicated design pattern for this, and it extends the Repository rule the
architecture skill already prescribes: *"repositories act as the single source of truth… 
responsible for presenting local or remote data, and should be the only place where data can be
modified"* `[OFFICIAL, High]`.

What follows from that single sentence:

- **The ViewModel never chooses between local and remote.** It asks the Repository; deciding
  which source answers is the Repository's job. A ViewModel holding an `isOffline` branch has
  taken on the Repository's responsibility.
- **Writes land locally first**, then push. The UI reflects the local write immediately rather
  than waiting on the network, which is what makes the app usable offline at all.
- **Reads can be served local-then-remote** — return cached data, fetch, emit again — which is
  why a Repository often returns a `Stream` rather than a `Future`.

Conflict resolution is the part the pattern does not decide for you: last-write-wins, per-field
merge, or server-authoritative are application decisions, and the choice belongs in an ADR
rather than implicitly in a Repository.

## Tokens: obtaining them, and what storing them does not buy

**Never ship a client secret.** A mobile app is a *public* client under OAuth 2.0: anything
compiled into it is extractable, which is the same rule as `flutter-build-release`'s obfuscation
point arriving from the auth side. The Authorization Code flow with **PKCE** exists precisely so
a public client needs no secret.

Use `flutter_appauth`, which wraps the native AppAuth SDKs, rather than hand-rolling PKCE — the
common hand-rolled error is getting `S256` wrong, producing a verifier the server rejects with
an opaque message. Authentication goes through the **external browser or a system web view**,
not an in-app `WebView`: an embedded web view can read the credentials and providers reject it.

**Secure storage protects data at rest, and only that.** Keychain on iOS and Keystore on Android
— RSA-OAEP plus AES-GCM by default on Android since `flutter_secure_storage` v10 — mean an
attacker with the device file system cannot read the token. They do not mean the token is safe
on a device the attacker controls.

> **[PRACTITIONER, Medium] — not a prescription.**
> Third-party AppSec analysis (Talsec) reports that data encrypted with Keystore-held keys
> remains reachable on a **rooted device, in a repackaged app, or through a runtime hooking
> framework** — the keys are usable by whatever runs as the app. No official Flutter document
> states these non-guarantees.
> *What would lift this:* a threat-model section on docs.flutter.dev/security, or a
> `flutter_secure_storage` README stating its limits explicitly.

**Biometrics are a presence gate, not a key.** `local_auth` answers "is the enrolled user here
right now"; it does not encrypt anything, and an item unlocked after authentication can stay
readable. Code that "protects" a token with biometrics alone has bought a UI prompt, not
confidentiality. Short-lived tokens and server-side revocation are what actually limit the blast
radius.

Redirect URI setup per platform, splitting `authorize` from `token`, and token storage layout:
[`references/auth-and-tokens.md`](references/auth-and-tokens.md).

## Key-value storage and generated clients

**The classic `SharedPreferences` API is legacy** — its own documentation points new users at
`SharedPreferencesAsync` / `SharedPreferencesWithCache` `[MAINTAINER, High]`, the two must not be
mixed in one app, and none of it is a place for tokens, since preferences are not encrypted.
**Typed client generators** — `retrofit` over `dio`, `chopper` over `http` — generate the Service
below the Repository from an annotated interface; they never remove the Repository.
Both branches, with the mixing hazard and the trade in full:
[`references/storage-and-clients.md`](references/storage-and-clients.md).

## Choosing a local database

Two of the popular options are unmaintained. Facts first, dated, because that is what is
sourceable `[MAINTAINER, High]` — verified 2026-08-03:

| Package | Status |
|---|---|
| `sqflite` | Maintained. Raw SQL over SQLite, async API |
| `drift` | Maintained. Typed SQL over SQLite, reactive `.watch()` queries, documented isolate support |
| `objectbox` | Maintained. NoSQL object store |
| `isar` | **Abandoned.** Last stable 3.1.0+1, 25 April 2023. Issue isar/isar #1689 (opened 7 January 2025) states verbatim *"Obviously, Isar is abandoned by @simc"* and points only to a *"Community Fork led by @vicenterusso"*. What remains is community forks — isar-community v3, isar_plus v4 — and 4.0.0-dev prereleases |
| `hive` | **Dormant.** Superseded in practice by the community fork `hive_ce` (Hive Community Edition) |

The one thing that follows from those facts without inventing a recommendation: **do not start a
new project on an unmaintained package**, and popularity is not maintenance — Isar and Hive are
still widely cited precisely because they were once the popular answer.

> **[PRACTITIONER, Low] — not a prescription.**
> Beyond maintenance status, no neutral comparison of these databases exists. The one structured
> comparison, `drift`'s FAQ, is **acknowledged as biased by its own maintainer** (Simon Binder),
> and Flutter publishes no guidance choosing between them.
> *What would lift this:* a neutral published comparison, or an official Flutter position.

What is decidable from documented capability rather than preference: relational queries and
migrations point to SQL (`sqflite`, `drift`); reactive queries that push on write are `drift`'s
`.watch()`; multi-isolate access needs documented support, which `drift` has; and web support
must be checked per package rather than assumed.

A `.watch()` stream is a subscription like any other — it leaks if it is not cancelled, and it
belongs on `flutter-runtime`'s `dispose` checklist.

## Database access from an isolate

**`sqlite3` is a synchronous C library.** Queries run on the isolate that calls them, so heavy
reads or writes issued from the root isolate block it and jank the UI — an `await` on a
`sqflite` call does not make the underlying work concurrent.

`drift` documents the way out `[MAINTAINER, High]`: `DriftIsolate.spawn` runs the database on a
background isolate, and that isolate calls
`BackgroundIsolateBinaryMessenger.ensureInitialized(token)` **before** opening the database,
because opening it goes through a plugin to resolve the file path.

The isolate mechanism itself — the token, persistent workers, and the fact that web has no
isolates at all, so this recipe has no web equivalent — is `flutter-runtime`'s.

## Seams

When a question sits near a seam, decide which side it falls on before answering.

| Neighbouring subject | Owner | Why the seam sits there |
|---|---|---|
| The UI/Data layer contract, the `Result` and `Command` types themselves, DI, `go_router` | `flutter-architecture` | Its doctrine of layers is its highest-value content; diluting it with transport detail costs more than the cross-reference |
| The isolate *mechanism* — `compute`, `Isolate.run`, persistent workers, `BackgroundIsolateBinaryMessenger` | `flutter-runtime` | One mechanism serves parsing, image work and database access, so it lives once. Only the `DriftIsolate.spawn` **recipe** is here |
| The `dispose` and subscription-cancellation checklist, leak diagnosis | `flutter-runtime` | Reactive query streams here cross-reference that checklist rather than restate it |
| Testing a Repository, faking a Service, mocking a plugin channel | `flutter-testing` | This skill writes the Repository; that one proves it |
| Running `build_runner` in CI, `pubspec` constraints, `dependency_overrides` | `flutter-build-release` | *When* generation is justified is a data-modelling question; *how it runs in a pipeline* is a build question |
| The Dart language — `sealed`, pattern matching, the `Isolate` API surface, async idioms | `dart-idioms` | Language layer, valid outside Flutter |
| Server-side Dart — shelf, Dart Frog, Serverpod | — | Outside this plugin |

## Name the silence

Official documentation is thinnest here and the third-party ecosystem most dominant. Say what
has no prescription, and what would lift it — an unlabelled claim gets obeyed as one.

Boxed where they appear above: concurrent refresh-token serialisation, comparative criteria
between local databases, and secure-storage non-guarantees on a compromised device. Still
unwritten, and silent when it is: at-rest encryption of a local database and its key handling —
generation, loss, recovery. That area carries no implied rule either way.

The line that governs all of them: dated **facts** are stated normally — Isar's abandonment is a
fact, not a flag — while a **recommendation** built on those facts is not.
